# Azure DevOps agent automation

Checked 2026-11-24. Scope: Azure DevOps Services, Azure Repos Git and Azure Boards. The Azure DevOps CLI extension targets the cloud service. Azure DevOps Server requires checking its own REST API version and authentication. [Microsoft CLI quickstart](https://learn.microsoft.com/en-us/azure/devops/cli/)

## 1. Azure CLI and PR automation

Install the `azure-devops` extension for Azure CLI. It adds `az devops` for organization and project operations, `az repos` for repositories and PRs, and `az boards` for work items. Ordinary Git commands still handle the working tree, branches, commits and pushes. [Extension quickstart](https://learn.microsoft.com/en-us/azure/devops/cli/) · [Azure DevOps CLI](https://learn.microsoft.com/en-us/cli/azure/devops?view=azure-cli-latest) · [Azure Repos CLI](https://learn.microsoft.com/en-us/cli/azure/repos?view=azure-cli-latest)

| Task | Interface |
|---|---|
| Create, list, inspect or update a PR | `az repos pr create`, `list`, `show`, `update` |
| Check out the PR locally | `az repos pr checkout --id PR_ID` from a clean local checkout. Current CLI has a `gh pr checkout` counterpart. |
| Manage reviewers and votes | `az repos pr reviewer add/list/remove`, `az repos pr set-vote` |
| Read, create or edit a ticket | `az boards work-item show/create/update` |
| Create or list PR discussion threads | `POST` or `GET` on `/_apis/git/repositories/{repositoryId}/pullRequests/{pullRequestId}/threads?api-version=7.1` |

The published PR CLI command list has no dedicated `comment` or `thread` command. Use the PR Threads REST API via `az rest` with an Entra bearer, or an HTTP client using the appropriate Azure DevOps credential. `az devops invoke` also provides generic REST invocation. Use the separate thread-comments endpoint to reply to an existing thread. [Azure PR CLI reference](https://learn.microsoft.com/en-us/cli/azure/repos/pr?view=azure-cli-latest) · [Azure Boards CLI reference](https://learn.microsoft.com/en-us/cli/azure/boards/work-item?view=azure-cli-latest) · [GitHub checkout reference](https://cli.github.com/manual/gh_pr_checkout) · [Create a thread](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-threads/create?view=azure-devops-rest-7.1) · [List threads](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-threads/list?view=azure-devops-rest-7.1) · [Reply to a thread](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-request-thread-comments/create?view=azure-devops-rest-7.1) · [Generic invoke](https://learn.microsoft.com/en-us/cli/azure/devops?view=azure-cli-latest#az-devops-invoke)

**Sign-in options.** `az login` signs in a Microsoft Entra user for the extension. `az devops login --organization URL` accepts a PAT at the prompt or on stdin. `AZURE_DEVOPS_EXT_PAT` supplies one to extension commands without that login step. Git over HTTPS has a separate credential flow, such as Git Credential Manager with Entra OAuth. Microsoft recommends Entra for new integrations because the bearer is short-lived, interactive sign-in can use MFA and Conditional Access, and workload identities can avoid long-lived personal credentials. An Entra OAuth token for Azure DevOps uses resource ID `499b84ac-1321-427f-aa17-267ca6975798`. [PAT sign-in](https://learn.microsoft.com/en-us/azure/devops/cli/log-in-via-pat) · [Authentication guidance](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/authentication-guidance) · [Entra tokens](https://learn.microsoft.com/en-us/azure/devops/cli/entra-tokens?view=azure-devops) · [Git credentials](https://learn.microsoft.com/en-us/azure/devops/repos/git/auth-overview)

## 2. PAT boundaries and workload identities

| Scope | Capability |
|---|---|
| `vso.code` | Read source, commits, branches and PR metadata. |
| `vso.code_write` | Push and manage code and PRs where the user has the necessary permissions. The create-thread endpoint also accepts this scope. |
| `vso.threads_full` | Read and write PR threads. Combine with `vso.code` for a reader that can post without code-write scope. |
| `vso.work` | Read work items and related metadata. |
| `vso.work_write` | Create and update work items. |

**Token scope and resource permissions.** Azure DevOps creates a PAT for a user and lets you choose the organization, expiry and capability scopes. The PAT has no project or repository selector. To achieve effective access to just one project or repo, use an identity with access confined there and review its inherited group grants. An existing broad user account retains its resource visibility where the PAT's capability applies. GitHub fine-grained PATs can name one resource owner and selected repositories at issuance, with permissions per capability. [PAT creation fields](https://learn.microsoft.com/en-us/rest/api/azure/devops/tokens/pats/create?view=azure-devops-rest-7.1) · [Azure DevOps scopes](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/oauth#scopes) · [Azure DevOps permissions](https://learn.microsoft.com/en-us/azure/devops/organizations/security/permissions?view=azure-devops) · [GitHub fine-grained PATs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens)

**Expiry and policy.** Choose the shortest usable expiry when creating the PAT. An Entra tenant administrator can cap new PAT lifetimes in days and restrict full-scoped or global PAT creation. A Project Collection Administrator can restrict creation and regeneration in one organization, with allowlist and packaging options. Microsoft documents a separate first-use rule for Entra-backed organizations: use a new PAT within 90 days or it becomes inactive. The current Azure DevOps Services retirement announcement schedules existing global PATs to stop working on 2027-01-27. Use an organization-scoped PAT when a PAT is required. [PAT lifecycle](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/use-personal-access-tokens-to-authenticate) · [Administrator policies](https://learn.microsoft.com/en-us/azure/devops/organizations/accounts/manage-pats-with-policies-for-administrators) · [Global PAT retirement](https://devblogs.microsoft.com/devops/retirement-of-global-personal-access-tokens-in-azure-devops/)

**Unattended automation.** Add an Entra service principal or managed identity to the Azure DevOps organization and grant project/repo rights inside Azure DevOps. Prefer a managed identity for an Azure-hosted workload, or workload identity federation for a service principal when supported. Obtain a short-lived Azure DevOps access token and use it with Git or REST as appropriate. [Microsoft workload identity guidance](https://learn.microsoft.com/en-us/azure/devops/integrate/get-started/authentication/service-principal-managed-identity)

**Azure Pipelines.** Azure Pipelines generates a job access token, exposed as `System.AccessToken`. Its effective rights depend on job authorization scope and the permissions of the project or collection Build Service. Use current-project scope and give `<Project> Build Service (<Organization>)` `Read` and `Contribute to pull requests` on the target repo to read and comment. Keep the token out of the reviewer process by mapping it only into the publishing step. PR validation for Azure Repos Git uses the target branch's Build validation policy. The pipeline sees the merged revision in that run. [Job access tokens](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/access-tokens) · [Predefined build variables](https://learn.microsoft.com/en-us/azure/devops/pipelines/build/variables) · [Repo permissions](https://learn.microsoft.com/en-us/azure/devops/organizations/security/permissions?view=azure-devops) · [Azure Repos PR triggers](https://learn.microsoft.com/en-us/azure/devops/pipelines/repos/azure-repos-git#pr-triggers)

## 3. Claude Code, Codex, MCP and Copilot

- **CLI:** Claude Code and Codex can read a work item using `az boards work-item show`, work in a local Azure Repos clone with Git, and open or update a PR using `az repos pr`. Use REST for discussion or the provided pipeline to review a PR diff with headless Claude. OpenAI also documents `codex exec` for non-interactive automation. [Course workflow](../cicd-headless/azure-devops/README.md) · [Claude Code programmatic usage](https://code.claude.com/docs/en/headless) · [OpenAI Codex non-interactive mode](https://developers.openai.com/codex/noninteractive)
- **MCP:** Microsoft's local `@azure-devops/mcp` stdio server uses Node.js and can reuse Azure CLI sign-in. It exposes tools for repositories, PRs and work items, including state changes where allowed. The Azure DevOps-hosted Streamable HTTP endpoint uses Entra OAuth and requires an Entra-backed organization. It is generally available. Microsoft's remote setup documents a custom Entra app registration for Claude Code and recommends the local server for Codex. Remote `X-MCP-Toolsets` and `X-MCP-Readonly` narrow the exposed operations. Azure DevOps identity permissions still apply. [Official server](https://github.com/microsoft/azure-devops-mcp) · [Local and remote overview](https://learn.microsoft.com/en-us/azure/devops/mcp-server/mcp-server-overview) · [Remote setup and client support](https://learn.microsoft.com/en-us/azure/devops/mcp-server/remote-mcp-server)
- **GitHub Copilot from Azure Boards:** The generally available work-item integration can start a coding task and link its draft PR back to the work item. It needs a connected GitHub repo using GitHub App authentication. The separately announced GitHub Copilot app integration with Azure Repos is in public preview and can work on Azure Repos branches and PRs. Copilot can use a work item's description via remote MCP, while Microsoft lists directly starting a coding session from a work item as a planned improvement for the app integration. Azure Repos Copilot Code Review became generally available on 2026-11-20. It is enabled at organization, project and repository level, can be requested manually (with an effort level) or automatically through the branch policy **Automatically request Copilot code review**, always leaves a non-blocking Comment review, is limited to 100 changed files and 100 changes per PR, and is billed to the linked Azure subscription in GitHub AI credits (1 credit = $0.01). Review rules come from `.github/` or `.azuredevops/copilot-instructions.md` and path-scoped `*.instructions.md` on the target branch. Course summary: [built-in option](../cicd-headless/azure-devops/README.md#built-in-option-copilot-code-review-in-azure-repos) [Azure Boards work-item integration](https://learn.microsoft.com/en-us/azure/devops/boards/github/work-item-integration-github-copilot) · [Copilot app preview](https://devblogs.microsoft.com/devops/azure-devops-integration-with-the-github-copilot-app-public-preview/) · [Copilot app with remote MCP](https://devblogs.microsoft.com/devops/azure-devops-and-github-start-your-agentic-journey-where-you-are/) · [Azure Repos Code Review general availability](https://devblogs.microsoft.com/devops/copilot-code-reviews-for-azure-repos-is-generally-available/) · [Get started with Copilot code review](https://learn.microsoft.com/en-us/azure/devops/repos/git/copilot-code-reviews?view=azure-devops) · [Copilot code review instructions](https://learn.microsoft.com/en-us/azure/devops/repos/git/configure-copilot-code-review-instructions?view=azure-devops)

## 4. GitHub data residency and Azure Repos

GitHub Enterprise Cloud with data residency uses GitHub repositories on a `*.ghe.com` domain and GitHub tooling, while Azure Repos runs in Azure DevOps with Azure DevOps authentication, permissions and APIs. [GitHub data residency](https://docs.github.com/en/enterprise-cloud@latest/admin/data-residency/about-storage-of-your-data-with-data-residency) · [Azure Repos authentication](https://learn.microsoft.com/en-us/azure/devops/repos/git/auth-overview)
